# 05. BF 가격 워치 — 기획안·개발계획

> **대원칙 (이 문서의 제1 제약)**: 계정정지 당하지 않고, 크롤링 의심을 받지 않으면서 목적을 달성한다.
> 기능과 안전이 충돌하면 [03 계정 보호 설계](03-account-safety.md)가 이긴다 — 예외 없음.
>
> 결정 기록 (2026-09-01): 워치 러너는 **VPS 분리 구축**으로 확정. 로컬(협업자 기기) 실행안은
> §4.1 물리 격리를 예외 처리해야 하고 가동률·회선 리스크를 떠안으므로 기각.
> VPS 방식은 [03 §4.1]을 예외 없이 그대로 충족한다.

## 1. 목표 / 비목표

### 1.1 목표

무신사 상품 링크만 주면, **워크스페이스를 새로고침했을 때** 그 상품의:

1. **작년 블랙프라이데이 할인율** (2025 무진장 BF — 수동 입력 기반, "수동" 배지 표기)
2. **올해 블랙프라이데이 할인율** (2026 — 자동 수집 스냅샷 기반)
3. **쿠폰 적용가** (공개 상품쿠폰가 — 최신 스냅샷 기준, "N시간 전 기준" 표기)
4. 연도별 가격 변화 추이 (매년 누적 — 2027년부터는 전년 대비가 완전 자동)

를 한눈에 볼 수 있다. **새로고침 = DB 읽기**다. 페이지뷰는 절대 무신사 요청을 발생시키지 않는다.

### 1.2 비목표 (하지 않는 것)

| 항목 | 이유 |
|---|---|
| 전 상품/카테고리 수집 | 저작권 안전선([03 §4.5]) + 조회 집합 최소화. **현표가 명시 등록한 상품만, 상한 30개** |
| 로그인 기반 개인화 가격 (등급할인·카드할인·최대혜택가) | 결제/로그인 전용 데이터. 불변식 1(무자격증명 채널)·Never List #2/#5로 **영구 금지** |
| 페이지 새로고침 시 실시간 조회 | 페이지뷰≠fetch 원칙. 예산 소모·봇 패턴 생성. 명시적 버튼 1클릭 = 1요청만 허용 |
| 2025년 데이터의 자동 복원 | 무신사는 가격 이력을 공개하지 않고, 임의 상품의 과거 아카이브를 가진 서드파티도 없음(2026-09 리서치). 수동 입력만 |
| 실시간·고빈도 추적 | 하루 1회(BF 기간 2회)로 충분. 빈도는 의심을 사는 유일한 변수이므로 최소로 고정 |

## 2. 요구사항별 실현 판정 (2026-09-01 조사 결과)

| 요구 | 판정 | 근거 |
|---|---|---|
| (a) 작년(2025) BF 할인율 | **수동 입력만 가능** | 앱 최초 마이그레이션 2026-08-26. 무신사 가격 이력 미공개(서드파티 트래커 전수 조사: 전부 자체 크롤링 축적, 임의 상품 과거 아카이브 없음) |
| (b) 올해(2026) BF 할인율 | **가능 — 단, 지금 착수 조건** | 10월 한 달의 행사 전 기준가 수집이 선행돼야 위장인상을 걸러낸 실할인율 계산 가능. 2025 BF는 11/16~26이었음(무진장 25 겨울, 뉴스룸 확인) |
| (c) 쿠폰 적용가 | **가능(공개 상품쿠폰가 한정)** | `couponPrice`는 비로그인 공개 페이로드에 "모든 사용자 동일"로 포함(활동 중인 서드파티 코드 5곳+ 교차 확인). 단 현 파서의 JSON-LD에 포함 여부는 실페이로드 1건으로 확정 필요. 실패 시 기존 수동 필드(`finalPrice`) 폴백 |
| (d) 새로고침 시 한눈에 | **가능(스냅샷 모델)** | 워크스페이스는 DB만 읽음. 별도 [새로고침] 버튼 = TTL 6h 캐시 우선 1회 요청(USER_URL 패턴) |

## 3. 안전 설계 — 왜 크롤링 의심을 받지 않는가

### 3.1 상속하는 기존 가드레일 (전부 그대로 적용)

- **Fetch Gateway 단일 관문**: 전역 600/일 하드캡, 호스트당 60/시간, 1req/5s+지터 U(0,5s), 동시성 1 ([02 §13]).
- **robots.txt 무조건 준수**: Disallow 제외, 조회 불가 시 보수적 거부(RFC 9309), 24h 캐시.
- **차단 시 뚫지 않고 멈춘다**: 429/403/captcha → 서킷 BLOCKED, **자동 재개 없음(사람 해제)**. 위장술(UA 로테이션·프록시 풀·captcha 우회) 금지 (Never List #7).
- **커미션 링크 절대 미방문**: ULID/utm 포함 URL 하드 abort. 워치는 정규 상품 URL만 방문 — 자기 클릭 어뷰징 원천 차단 ([03 §5.4]).
- **식별자 위생**: UA는 봇 정직 표기 1종, 계정 연관 문자열(jenflox/현표/개인 이메일) 금지 — CI 검사 ([03 §4.1]).
- **본문 미저장**: FetchLog는 URL·응답코드만. 스냅샷은 가격/쿠폰 필드만 저장(설명문·이미지 저장 금지 — 잡코리아 판례 안전선).

### 3.2 워치 전용 규율 (신설 — 구현 시 [02 §13] 정책 시트에 편입)

| 항목 | 값 | 이유 |
|---|---|---|
| 워치 등록 상한 | **30개** (소프트캡, DB policy) | 추적 상한 200개의 15%. "현표가 직접 고른 소수"라는 스코프를 수치로 강제 |
| 기본 빈도 | **1회/일/상품** | 사람이 관심 상품을 하루 한 번 보는 것과 같은 총량 |
| BF 기간 빈도 | 2회/일 (이벤트 창 설정 시에만) | 행사가 캡처 누락 방지. 피크 60req/일 — 전역 캡의 10% |
| 실행 시각 | 일 1회 랜덤 슬롯 + 지터, **헬스체크와 다른 시간대** | 호스트당 60/시간 캡을 헬스체크와 공유하므로 겹치면 서킷 조기 정지(안전하지만 커버리지 손실) |
| 순회 순서 | 매 사이클 셔플 | 고정 순서 순회 지문 제거 |
| 워치 만료 | 등록 후 90일 자동 해제 (BF 종료 시 일괄 해제 권장) | 목적 종료 후 트래픽 잔존 방지 |
| 실행 위치 | **VPS 전용** (현표 기기·IP·발행 서버와 분리) | [03 §4.1] 물리 격리 — 예외 없이 충족 |
| 조회 대상 | WatchItem에 등록된 정규 상품 URL만 | 조회 집합 = "본인이 다루는 소수 딜"로 한정 ([03 §4.3] 지문 완화) |

### 3.3 1일차 게이트 (가동 전 필수 — [04 로드맵] 리드타임 #8과 동일)

VPS 확보 즉시, 워치 가동 **전에**:

1. VPS IP에서 `robots.txt` 실측 — `/products/*` 허용 여부 확인, 결과를 본 문서 §9에 기록.
2. 저빈도 단건 fetch 실측 — 데이터센터 IP에 대한 챌린지/차단 여부 확인.
3. **막히면 뚫지 않고 §3.4 크롤리스 모드 확정.** 우회 시도는 하지 않는다.

### 3.4 크롤리스 폴백 모드 (차단 시나리오가 기본 가정)

[04 리스크 레지스터]대로 "무신사 크롤링 차단"은 확률 중~높음이다. 막혀도 기능은 죽지 않는다:

- WATCH 트리거 영구 오프. 스냅샷은 USER_URL(링크 재던지기)·MANUAL만으로 축적.
- 텔레그램 봇이 **리마인더**로 전환: BF 기간 등 지정 기간에 "오늘 워치 목록 N개 — 앱에서 열고 다시 던져주세요"
  + 워치 목록 링크 일괄 전송. 사람이 탭하는 건 봇 트래픽이 아니다.
- 무신사 협의 트랙(봇 정식 통지·robots 정책 확인 — 진행 중) 결과에 따라 재평가.
- **제휴 성사 시 워치 러너 전면 폐기가 성공 시나리오다** ([04 Phase 5]와 동일 원칙).

### 3.5 로드맵 순서와의 관계

이 기능은 Phase 3 "딜 레이더"의 **축소 선행 트랙**이다(레이더의 Tracker 서브셋, 발굴 없음).
순서 원칙("루프 습관화 → 헬스체크 신뢰 → 레이더")상 헬스체크(Phase 2) 신뢰 획득 후 단계이며,
Phase 3 본체의 1일차 게이트(§3.3)를 그대로 선행 이행한다. 여기서 구축하는 VPS·게이트 실측·WATCH
트리거는 Phase 3 레이더가 그대로 물려받는다 — 선행 투자이지 우회가 아니다.

## 4. 아키텍처

### 4.1 구성

```
[현표 폰]──링크 던지기──▶[텔레그램 봇]──┐
[협업자 PC]  Next.js 웹앱(워크스페이스)  ├──▶ [공유 DB: Supabase Postgres]
                                        │         ▲
[VPS (신규, 분리 IP)]                    │         │ PriceSnapshot INSERT
  └─ 워치 러너 (cron, 1회/일) ──▶ Fetch Gateway ──▶ 무신사 (정규 상품 URL만)
```

- 발행·승인·수동 경로는 전부 기존 그대로. **워치 러너만 VPS에 산다.**
- VPS 스펙: 1vCPU/1GB, 서울 리전, 월 ~5천원(또는 Oracle Free Tier $0). Node 20 + 리포 체크아웃 + systemd 타이머.
- VPS에는 플랫폼 토큰 일절 미주입([03 §4.1] 자격증명 제로) — DB 커넥션 문자열(스냅샷 쓰기 권한)만.

### 4.2 DB 이관 (SQLite → Supabase Postgres)

VPS와 로컬 앱이 같은 DB를 봐야 하므로 파일 DB로는 불가. **Supabase Free로 이관**한다.

- 근거: [04 비용표]에 이미 Supabase Free가 MVP 스택. [03 §7](Vault)·[03 §11](PITR 백업)·[02 §8.1]
  (Phase 3 인프라)이 전부 Supabase 전제 — 예정된 이관의 앞당김이지 신규 결정이 아니다.
- Prisma datasource provider 전환 + 마이그레이션 재생성. 현재 데이터는 개발용이므로 재시드 허용
  (실데이터 존재 시 export/import).
- 로컬 앱·봇·VPS 러너가 동일 커넥션 사용. 백업: 리드타임 #9(pg_dump 크론) 이 시점에 함께 이행.

### 4.3 스키마 추가 (prisma/schema.prisma)

```prisma
model PriceSnapshot {
  id          String   @id @default(cuid())
  productId   String
  product     Product  @relation(fields: [productId], references: [id])
  capturedAt  DateTime @default(now())
  listPrice   Int?     // 정가
  salePrice   Int?     // 행사가(판매가)
  couponPrice Int?     // 공개 상품쿠폰가 (파서 확장 전/실패 시 null)
  source      SnapshotSource   // USER_URL | HEALTH_CHECK | WATCH | MANUAL
  eventTag    String?  // "BF2025" | "BF2026" | null — 이벤트 창 설정으로 자동 스탬핑, MANUAL은 직접 지정
  note        String?  // MANUAL 입력 근거(예: "작년 스크린샷 기준")
  @@index([productId, capturedAt])
}

model WatchItem {
  id        String   @id @default(cuid())
  productId String   @unique
  product   Product  @relation(fields: [productId], references: [id])
  createdAt DateTime @default(now())
  expiresAt DateTime // 기본 +90일
  active    Boolean  @default(true)
}

enum FetchTrigger { USER_URL HEALTH_CHECK RADAR ROBOTS WATCH }  // WATCH 추가
```

- 스냅샷 기록 3경로(전부 **추가 요청 0건**):
  ① USER_URL — 봇에 링크 던질 때(현재는 Product upsert로 덮어쓰며 이력 소실 → 기록 추가),
  ② HEALTH_CHECK — 헬스체커가 이미 전체 HTML을 내려받아 `parseProductPage`를 호출하고 결과를 버림
  (`src/lib/health-check.ts` `judgeAvailability`) → 파싱 결과를 밖으로 끌어내 저장,
  ③ MANUAL — 작년 BF가 수동 입력 폼.
- ④ WATCH만 신규 요청을 발생시키며 §3.2 규율을 따른다.

### 4.4 할인율 정의 (위장인상 방어)

- **기준가** = 해당 상품의 10/1~BF 전날 스냅샷 `salePrice` **중앙값** ([02 §8.2] PRICE_DROP의 30일 중앙값 필터와 동일 사상).
- **BF 실할인율** = (기준가 − BF `salePrice`) / 기준가 — **헤드라인 수치**.
- 정가 대비 할인율 = (`listPrice` − `salePrice`) / `listPrice` — 참고 병기(무신사 표기와 대조용).
- 쿠폰 반영 할인율 = (기준가 − `couponPrice`) / 기준가.
- 기준가 스냅샷이 3개 미만이면 실할인율 미표기("기준가 수집 부족") — 단일 시점 비교 금지.

### 4.5 쿠폰가 파서 확장

- 순서: **실페이로드 1건 캡처 → JSON-LD에 쿠폰가 있으면 그대로**(파서 변경 최소) →
  없으면 `__NEXT_DATA__` 파싱 추가 — [02 §5.1]이 이미 승인한 폴백 체인(JSON-LD → NEXT_DATA → DOM → 수동)의 이행.
- 무신사는 내부 필드를 예고 없이 개명한 전례(`__MSS__`→`__MSS_FE__`)가 있으므로: 파싱 실패는 에러가 아니라
  **null + 수동 필드(`Deal.finalPrice`) 폴백 + 텔레그램 알림**. `memberPrice`는 의미 미확인이므로 저장·표시하지 않는다.

### 4.6 UI/UX

- **워크스페이스(비공개) 전용.** 공개 허브에는 어떤 형태로도 노출하지 않는다.
- 딜 카드 3칸 스트립: `[작년 BF 38% (수동)] [올해 BF — 추적중 D-76] [쿠폰가 ₩41,300 · 6시간 전 기준]`
  + 스냅샷 스파크라인. 데이터 없음 상태 명시: "기록 없음 · 수동 입력", "기준가 수집 중", "아직 스냅샷 없음".
- [새로고침] 버튼: 최신 스냅샷이 6h 이내면 캐시 응답(요청 0건), 아니면 USER_URL 1회. 게이트웨이 거부
  (BLOCKED_*)는 사유 그대로 표기.
- 텔레그램: 상품 카드에 [BF까지 추적] 버튼(= /watch), `/watchlist`, `/unwatch`. 등록 시 상한(30)·만료 안내.
- 작년 BF 수동 입력: `/bf2025 <가격>` 또는 워크스페이스 폼 → MANUAL 스냅샷(eventTag=BF2025, "수동" 배지).

### 5.2 VPS 배포 절차 (W2-인프라)

```bash
# 1) VPS에 리포 체크아웃 + 의존성
git clone <repo> qurator && cd qurator && npm ci
# 2) .env — DATABASE_URL(공유 Postgres)만. 플랫폼 토큰은 절대 주입하지 않는다(docs/03 §4.1)
#    TELEGRAM_*·APP_ACCESS_TOKEN·ANTHROPIC_API_KEY 없음
# 3) 게이트 실측 — 이 단계를 건너뛰고 가동하지 않는다 (§3.3)
curl -sS https://www.musinsa.com/robots.txt | head -40   # /products 허용 여부 확인 → §9에 기록
npm run watch -- --dry                                    # 대상만 확인(요청 없음)
# 4) 게이트 통과 후에만 1회 수동 실행으로 확인
npm run watch
```

systemd 타이머 (하루 1회, **헬스체크와 다른 시간대**, 랜덤 지연):

```ini
# /etc/systemd/system/qurator-watch.timer
[Timer]
OnCalendar=*-*-* 04:00:00        # 헬스체크(로컬 6h 루프)와 겹치지 않는 시간대
RandomizedDelaySec=3600          # 고정 시각 지문 제거 — 매일 04:00~05:00 사이 랜덤
Persistent=true                  # 재부팅으로 놓친 실행을 따라잡는다
```

> 예산 주의: 시간당 60건 캡을 헬스체크와 **공유**한다. 같은 시각에 겹치면 한쪽이
> `BLOCKED_BUDGET`으로 조기 종료된다(안전하지만 그날 커버리지 손실).

- 개발 순서의 원칙: **W0이 가장 먼저다.** 스냅샷 피기백은 VPS·이관과 독립적으로 지금 바로 가치를 만들고,
  하루 늦어질수록 기준가 이력이 하루 사라진다.
- W1~W2가 1주씩 밀려도 10/1 데드라인까지 2주 버퍼가 있다. W3(쿠폰가)는 밀려도 나머지와 독립.

## 6. 리스크 레지스터

| 리스크 | 확률 | 대응 |
|---|---|---|
| robots.txt가 /products 차단 | 중~높음 | §3.3 게이트에서 확정 → §3.4 크롤리스 모드(리마인더 봇). 뚫지 않는다 |
| 데이터센터 IP 챌린지/차단 | 중 | 동일 — 게이트 실측으로 조기 판정. 프록시·위장 전환 금지, 협의 트랙 대기 |
| 파서 깨짐(무신사 개편·필드 개명) | 중 | null 폴백 + 수동 필드 + 알림. 상태 동결 원칙([04 리스크]와 동일) |
| 60/시간 캡을 헬스체크와 나눠 씀 | 낮음 | 시간대 분리(§3.2). 겹쳐도 BLOCKED_BUDGET 조기 정지 = 설계된 안전 동작 |
| VPS 장애/미결제로 조용히 멈춤 | 낮음 | 러너가 사이클 완료 시 heartbeat 기록 → 48h 무기록 시 텔레그램 알림 |
| 2026 BF 일정 미공지 리스크 | 낮음 | 이벤트 창은 설정값 — 공지 후 입력. 기본 1회/일 수집은 일정과 무관하게 유효 |
| 무신사 측 항의·요청 수신 | 낮음 | **즉시 전면 중단**이 기본 대응([03 §4.3]) — 워치 킬스위치는 수집기 독립 킬스위치([03 §6.2-3])에 편입 |

## 7. 하지 않기로 확정한 것 (재론 방지)

1. 로컬(협업자 기기) 워치 실행 — §4.1 예외가 필요해지므로 기각 (2026-09-01).
2. 페이지뷰 트리거 fetch — 어떤 형태로도 금지.
3. 로그인·쿠키·개인화 가격 접근 — 영구 금지 (불변식 1).
4. 30개 초과 확장·발굴(디스커버리) 기능 — 그건 Phase 3 레이더의 일이며 별도 게이트를 거친다.
5. 차단 우회 일체 (UA 위장·로테이션·프록시 풀·captcha) — Never List #7.
