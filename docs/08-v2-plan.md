# 08. qurator 2.0 — LTK 벤치마킹 기획안·개발계획

> **한 줄 결론**: LTK에서 가져올 것은 *화면*이 아니라 **정보구조와 진입점**이다 —
> "홈 = 오늘 할 일 + 성과", "한 손가락 진입점(+ 버튼·공유 시트)", "저장 → 발행 → 성과가 한 앱에서 닫히는 루프".
> 우리가 이미 LTK보다 나은 것(스크린샷 인식·위장할인 판정·고지 자동화·죽은 링크 방어)은 그대로 두고,
> 없는 것 3가지(성과 화면·앱다운 진입점·허브 정보량)만 채운다. 크리에이터 1명이 혼자 쓰는 앱이므로
> LTK의 플랫폼 기능(검색·소셜·채팅·예약·브랜드 협업)은 **가져오지 않는다**.
>
> 전제: 1차 사용자 현표 1명([01 §1]). 절대 원칙([README])은 이 문서에서도 그대로다 —
> 계정 보호 > 기능, 발행은 항상 휴먼 승인 게이트 뒤, 무신사 요청 0건 원칙 유지.
>
> 조사 한계: LTK 공식 발표·앱스토어 설명·크리에이터 튜토리얼·리뷰 기사를 근거로 했고(§5 출처),
> 앱을 직접 설치해 화면을 만진 것은 아니다. 세부 화면 배치는 버전마다 바뀌므로 §1은 "구조"에 집중한다.

## 1. LTK 분석

### 1.1 무엇인가

LTK(구 rewardStyle/LIKEtoKNOW.it)는 **크리에이터 커머스 플랫폼**이다. 크리에이터가 상품을 태그한 포스트를
올리면 팔로워가 LTK 앱·웹에서 그 포스트를 보고 구매하고, 크리에이터는 리테일러가 정한 커미션을 받는다.
8,000+ 리테일러·100만 브랜드·4.5억 상품 카탈로그, 커미션은 평균 10~25%(최대 30%)로 리테일러가 정한다.
앱은 **두 개**로 나뉜다 — 크리에이터용 *LTK Creator*와 쇼퍼용 *LTK*.

우리와의 결정적 차이 두 가지를 먼저 적어둔다:

1. **LTK는 멀티 리테일러·API 기반**이다. 링크 생성·커미션 조회·정산이 전부 플랫폼 안에서 API로 된다.
   우리는 무신사 단일, 링크는 큐레이터센터에서 사람이 만들고, 무신사는 크롤링을 막는다([05 §9]).
   → LTK의 "검색·비교·자동 링크" 계열은 **구조적으로 이식 불가**하며, 이식할 필요도 없다.
2. **LTK의 발행 지면은 LTK 자체 앱**이다. 우리의 발행 지면은 카톡 오픈채팅·스레드·인스타·노션이고,
   LTK 포스트에 해당하는 것은 우리의 **링크허브(`/hub`)** 한 곳뿐이다.

### 1.2 크리에이터 앱 구조 (탭 단위)

| 탭 | 하는 일 | 비고 |
|---|---|---|
| **Home** | 기간 선택 → 총수익(커미션+협찬 고정비)·방문·판매·월별 추이. 상단에 "오늘 볼 것" | 앱을 열면 *성과*가 먼저 보인다. 2024년 개편으로 인사이트가 홈으로 올라옴 |
| **Create & Publish** | 우하단 **큰 + 버튼** → Add Media → Add Caption(+해시태그 3개) → Add Products(My Folders 또는 Brand Sites에서 태그) → **Publish / Schedule** → 소셜에 텍스트·링크 공유 | 포스트 1건 = 사진 + 태그 상품 + 캡션. 예약 발행 내장 |
| **Search** | 4.5억 상품 검색, 13개 카테고리, 필터(High Commissions·New on LTK·Active Collabs 등), **상품별 커미션율 비교** | 2024-09 신설. 우리에겐 해당 없음(무신사 단일·API 없음) |
| **Analytics** | 클릭·주문·전환율·판매 수량·포스트별 참여, **Top 상품·Top 브랜드·채널별 포스트 성과**. 클릭은 90분, 나머지는 매일 밤 갱신 | "무엇이 실제로 팔리는가"를 앱 안에서 본다 |
| **Profile(Shop)** | 배너·프로필·바이오, 포스트를 **컬렉션·기프트 가이드**로 묶어 상단 노출. 인스타 그리드처럼 보이는 스토어프론트 | 팔로워가 보는 지면 = 우리의 `/hub` |

### 1.3 핵심 워크플로

**(a) 링크 만들기** — 브라우저에서 상품 페이지를 열고 **공유 시트 → LTK Creator**를 누르면
폴더에 저장하거나 즉시 링크를 받는다. 앱을 "열러 가는" 동작이 없다.

**(b) 포스트 만들기** — `+` → 미디어 → 캡션 → 상품 태그(저장해 둔 폴더에서 고른다) → 발행/예약.
포스트 후 "소셜에 공유"는 **텍스트 복사 또는 링크 복사**다 — 결국 크로스포스팅은 우리처럼 반자동이다.

**(c) 성과 보기** — Home에서 숫자를 보고, Analytics에서 Top 상품을 본다. 다음 포스트의 소재가 여기서 나온다.

세 흐름이 **저장(폴더) → 발행(포스트) → 성과(Analytics) → 다시 저장**으로 한 앱 안에서 닫힌다.

### 1.4 쇼퍼 앱에서 배울 것

- **♥ 저장 → 가격 인하 알림.** 쇼퍼가 하트한 상품이 세일하면 알림을 보낸다.
- **"Price Drop" · "Back in Stock" 배지**가 상품에 붙는다. 상태를 배지 하나로 말한다.
- 2025-07: 비주얼 서치(사진으로 비슷한 포스트 찾기), AI 검색, 공개 프로필, 양방향 채팅. 2025-02: 비디오 우선 피드.

우리의 팔로워는 계정이 없고(카톡·스레드에서 링크를 누를 뿐) 푸시를 보낼 대상도 아니므로, 알림은 이식하지 않는다.
대신 **배지는 허브에 그대로 쓸 수 있다** — 우리는 가격 스냅샷을 이미 갖고 있어서 "가격 인하"·"최저가"·"쿠폰 마감 D-n"을
계산할 수 있다. LTK는 리테일러 피드로 하는 일을 우리는 스크린샷 스냅샷으로 한다.

### 1.5 UI/UX 평가 — 정직한 판정

LTK가 "디자인이 깔끔한 앱"으로 꼽히는 것은 아니다. 크리에이터 커뮤니티의 비교글은 오히려 **LTK의 UX가
복잡하고 도움말이 부족하다**고 하고, 경쟁 서비스(ShopMy)를 "미니멀·직관적"으로 평가한다([§5] 출처 12·13).
LTK의 강점은 화면의 미학이 아니라 **구조**다:

| LTK가 잘하는 것 | 우리에게 적용하면 |
|---|---|
| 앱을 열면 성과가 먼저 (Home) | 지금 우리 홈은 "캡처 버튼 + 딜 목록"뿐. 어제 올린 딜이 얼마나 눌렸는지 볼 곳이 없다 |
| 한 손가락 진입점 — `+` 버튼·공유 시트 | 지금은 사진첩 파일 선택창을 거친다(2탭). 공유 시트에서 바로 받으면 1탭 |
| 저장함(My Folders) — 지금 안 올릴 것을 잃지 않는다 | 우리의 [📈 가격만 지켜보기]가 사실상 이것. 이름과 위치가 "가격 추적"으로 좁게 잡혀 있다 |
| 컬렉션 — 팔로워 지면을 주제로 묶는다 | 허브는 최신순 40개 평면 목록 |
| Analytics — Top 상품·채널별 | 클릭 계측(`ClickEvent`·`surface`)은 이미 쌓이는데 **보여주는 화면이 없다** |
| 네이티브 앱 — 아이콘·풀스크린·알림 | 웹앱인데 manifest도 없다(홈 화면 추가 시 브라우저 UI가 남는다) |

LTK가 못하는 것 — 우리가 지킬 것: 가격 이력·실할인율 판정(LTK에는 없다), 고지문 자동 삽입·검증,
죽은 링크 자동 숨김, "본 것 = 나가는 것" 미리보기, 계정 자격증명 제로.

### 1.6 LTK 설계 원칙 요약 (이식 대상)

1. **홈은 대시보드다** — 열자마자 "오늘 할 일 + 어제의 결과".
2. **진입점은 하나, 항상 같은 자리** — 우하단 `+`. 그리고 OS 공유 시트.
3. **저장과 발행을 분리** — 지금 안 올려도 잃지 않는다.
4. **성과가 다음 소재를 정한다** — Top 상품이 한 화면에.
5. **팔로워 지면은 상태를 배지로 말한다** — Price Drop / Back in Stock.

| 영역 | LTK | qurator (2026-09 현재) | 판정 |
|---|---|---|---|

| 팔로워 지면 | Shop(배너·바이오·컬렉션·배지) | `/hub` 평면 목록, 고지 배너, 품절 자동 숨김 | **부족** — 정보량. 자동 숨김·고지는 앞섬 |
| 가격 정보 | 현재가만 | 스냅샷 이력·실할인율·위장할인·작년 BF 비교 | **앞섬** — 허브에도 쓸 수 있다 |
| 알림 | 푸시(크리에이터·쇼퍼 모두) | 대시보드 상단 목록(열어야 보임) | 부족하나 **선택** — 1인 사용자는 매일 열기로 충분할 수 있음 |
| 앱 형태 | 네이티브 iOS/Android | 웹(Vercel), manifest 없음 | **부족** — PWA 최소 요건만 채우면 90% 해소 |
| 안전·규정 | 플랫폼이 책임 | 자격증명 0·approval-first·고지 불변식·감사 로그 | **앞섬** — 유지 |
| 도움말 | 부족하다는 평 | 카드 안 [❓ 버튼 설명] | 동급 이상 |

### 2.1 우리가 앞서는 것 — 2.0에서도 손대지 않는다

- 스크린샷 → Vision 캡처([06]), 여러 장 병합, 이미지 미저장.
- 실할인율·위장할인 판정·"그때 얼마 → 지금 얼마"([05]).
- 렌더러 + 고지 하드 삽입 + 발행 전 검증 게이트, 카드 1장 상태 전이([02 §6]).
- 숏링크·헬스체커·허브 자동 숨김·정정문 원탭([README Phase 2]).
- Fetch Gateway·크롤리스 모드·킬스위치([03]).

## 3. qurator 2.0 기획안

### 3.1 목표

| 지표 | 현재 | 2.0 |
|---|---|---|
| 캡처 진입 탭 수 (폰 홈 → 사진 선택 완료) | 3~4 | **1~2** (공유 시트 / FAB) |
| "지난주 뭐가 눌렸나" 확인 | 불가 | **홈에서 3초** |
| 진행 중 딜 30개일 때 특정 딜 찾기 | 스크롤 | **필터·검색 1탭** |
| 허브에서 팔로워가 "지금 살 이유"를 보는가 | 가격만 | **배지 1개 이상** |
| 주간 사용일([04 KPI]) | — | 7/7 유지·개선 |

### 3.2 정보구조 — 하단 탭 4개 + FAB

```
┌──────────────────────────────┐
│  홈    딜    성과    설정     │  ← 하단 탭(엄지 영역). 허브는 설정 안 "허브 열기"
└──────────────────────────────┘
                     ( 📷 )     ← FAB. 모든 탭에서 같은 자리. 탭하면 사진첩(멀티 선택)
```

| 탭 | 내용 | 지금 어디에 있나 |
|---|---|---|
| **홈** | ① 오늘 할 일: 승인 대기 n · 링크 대기 n · 기록할 상품 n · 정정 공지 n (각각 탭하면 딜 탭 해당 필터로) ② 지난 7일: 클릭 / 발행 / 허브 방문 3칸 ③ 최근 캡처 5건 | 현재 홈 상단 섹션들 + 없음 |
| **딜** | 컴팩트 리스트. 상단 필터 칩: `전체 · 후보 · 링크 대기 · 승인 대기 · 저장함 · 승인 완료 · 기록 완료`. 검색(브랜드·상품명). 행 탭 → 상태 카드(현재 `DealStageCard` 그대로)가 시트로 펼쳐짐 | 현재 홈 본문 + `/watch` 목록 |
| **성과** | 기간 토글 7일/30일. 총 클릭(봇 제외) · 채널별(surface) 막대 · 딜별 Top 5 · 허브 CTR(방문 대비 클릭). 하단 "정산 입력"(옵션): 큐레이터센터 정산 화면 스크린샷 → Vision → 월 매출 1줄 | 없음 (`ClickEvent`만 존재) |
| **설정** | 프로필(핸들·큐레이터샵 URL·허브 한 줄 소개) · 허브 열기 ↗ · 작년 BF 가격 입력(현재 `/watch` 하단 폼) · 가격 추적 상한 표시 · 접근 토큰 재발급 안내 | `/watch` 하단 + 없음 |

카드 1장의 상태 전이·버튼 문구([06 §3.0])·미리보기 원칙([02 §6])은 **한 글자도 바꾸지 않는다.**
바뀌는 것은 카드가 놓이는 자리(리스트 → 시트)와 그 주변(탭·필터·FAB)이다.

### 3.3 화면별 명세

**홈**
- "오늘 할 일"이 비면 그 블록 자체를 그리지 않는다(없는 데이터를 그리지 않는다 — `PriceStrip` 원칙 그대로).
- 7일 3칸은 `ClickEvent`(uaClass=human)·`Post`(SENT/CONFIRMED)·허브 방문(신규 계측 §3.4) 집계. 숫자 옆에 전주 대비 화살표 하나.
- 캡처 결과(“카드를 만들었습니다”·가격 변화 노트)는 인라인 박스가 아니라 **토스트 + 딜 탭 자동 이동**.

**딜**
- 행: `[단계 칩] 브랜드 · 상품명` / `가격줄` / 우측 상대시각. 판정 첫 줄([06 §3.1])이 있으면 칩 옆에 이모지 1개.
- 시트: 현재 `DealStageCard` 전체. 시트 상단에 닫기. 시트 안 액션 후에는 리스트로 돌아오며 행이 갱신.
- 승인 완료 30일 경과 → "보관" 필터로 이동(삭제 아님, 허브 노출 로직과 무관).
- 검색은 클라이언트 필터(60건 → 최대 300건 로드로 상향, 그 이상은 서버 페이지네이션 — 2.0 범위 밖).

**캡처 진입점**
- FAB: 현재 `ScreenshotCapture`의 input을 재사용. 직접 입력 폼은 FAB 길게 누르기 대신 **딜 탭 상단 "✏️ 직접 입력"** 링크로 유지(발견 가능성).
- **Web Share Target**(`manifest.share_target`, `POST multipart`, `image/*`): Android Chrome에서 무신사 앱 → 공유 → qurator 선택 → 스크린샷이 `/api/capture`로 직행. 결과는 딜 탭 + 토스트.
- iOS: PWA는 share target 미지원. **단축어 레시피**를 설정 탭에 안내(“최근 스크린샷 → qurator 열기”). 실측 후 문서화.

**성과**
- 집계는 서버에서 SQL로(`groupBy`), 페이지는 DB만 읽는다(무신사 요청 0건 불변식 유지).
- 딜별 Top 5 행을 탭하면 딜 시트. "이 딜 다시 올리기" 같은 재발행 액션은 넣지 않는다([02 §7.3] 재발행 규칙은 어댑터 몫).
- 정산 입력(옵션): 스크린샷 → Vision(기존 `vision-extract` 패턴, 별도 스키마) → `Settlement{month, amountKRW, source:SCREENSHOT}` 1행. 상품별 매칭은 하지 않는다(무신사 정산 화면 형식 미확인 — §4.3 열린 질문).

**허브 v2**
- 배지 규칙(스냅샷·딜 필드만 사용, 요청 0건):
  - `가격 인하` — 최신 스냅샷 salePrice < 직전 스냅샷
  - `최저가` — 최신이 기록된 모든 스냅샷 중 최저 (표본 ≥3)
  - `쿠폰 마감 D-n` — `couponExpiresAt` 기준, D-0은 "오늘 마감"
  - 우선순위 1개만 표시: 쿠폰 마감 > 최저가 > 가격 인하
- 섹션: `Deal.tags`(JSON 문자열, 예 `["가을 아우터"]`)가 있으면 태그별 섹션, 없으면 "오늘의 꿀매" 한 섹션(현재와 동일).
- 한 줄 소개(`Creator.bio`)를 핸들 아래에. 배너·아바타는 넣지 않는다(이미지 자산 관리가 생긴다).
- 허브 방문 계측: `HubVisit{ts, uaClass}` — IP 미저장, 봇 분류만(`ClickEvent`와 동일 규율).

**설정**
- 현재 `/watch`는 사라지고 워치 목록은 딜 탭 "저장함", BF 수동 입력은 설정으로.

### 3.4 데이터 모델 변경 (최소)

| 변경 | 이유 |
|---|---|
| `Deal.tags String?` (JSON 배열) | 허브 섹션. 별도 Collection 테이블은 1인 사용에 과하다 — V2-D |
| `Creator.bio String?` | 허브 한 줄 소개 — V2-D |

기존 enum·불변식(`ShortLink` 원형 무변조, `ContentCard` 불변 등)은 변경 없음. 마이그레이션 1개.

### 3.5 디자인 원칙 — 벤치마크는 ShopMy

> **결정 (2026-09-15)**: 구조는 LTK(§1.6), **디자인은 ShopMy**를 벤치마크한다. 크리에이터 비교글이 일관되게
> "LTK보다 깔끔하고 쉽다"고 평하는 쪽이고, 우리 결(미니멀·정보 우선)과 맞는다. 인접 카테고리에서는
> Stan Store(앱스토어 4.9)가 "링크 목록이 아니라 스토어"라는 프레이밍으로 호평인데, 그 관점은 허브 v2에만 빌린다.

ShopMy에서 가져오는 구체적 특징:

| ShopMy | qurator 2.0 적용 |
|---|---|
| 스토어프론트 = **섹션(상단 탭) + 컬렉션(주제 묶음)**. "링크 더미"가 아니라 "부티크"로 보인다 | 허브 v2: 태그 섹션(§3.3), 가격·배지 한 줄, 링크 나열 금지 |
| 크리에이터가 **Latest Finds / Most Popular** 순서를 고른다 | 허브 상단에 "최신" · "많이 본" 두 블록. 순서는 설정에서 |
| 커미션 안 붙는 상품도 컬렉션에 넣을 수 있다(폐쇄형 아님) | 큐레이터 링크 없는 딜도 태그·저장함에 둘 수 있다(발행만 막힘 — 기존 불변식) |
| 성과는 **Links / Earnings / 컬렉션별** 세 곳, 실시간 클릭·주문 | 성과 탭: 딜별·채널별·(태그별) — 표 하나, 그래프는 막대 1종 |
| 모바일 앱은 값을 흐리게 가리고 웹에서 상세 | 우리는 1인용이라 가리지 않는다. 대신 성과 탭도 게이트 뒤 |
| 여백·흰 바탕·가는 구분선·굵기로만 위계 | 카드 테두리 최소화, 색은 배지·주 버튼에만, 아이콘보다 문구 |

1. **미니멀을 유지한다.** LTK의 그리드·배너·피드는 가져오지 않는다. ShopMy처럼 "정돈된 부티크"가 목표다.
2. **한 손.** 주 동작은 하단(탭·FAB·카드의 주 버튼). 상단에는 읽기만.
3. **상태는 색이 아니라 문구로.** 칩 텍스트가 곧 상태. 색은 보조.
4. **없는 데이터를 그리지 않는다.** 빈 블록은 사라진다. 표본 부족은 "수집 중 (2/3)".
5. **화면 이동보다 시트.** 카드 안에서 폼이 열리는 현재 원칙([06 §10-4])을 리스트에도 적용.
6. **글씨는 16px 이상**(iOS 자동 줌 방지, `CopyPane` 주석과 동일).

### 3.6 안전 불변식 — 2.0에서 새로 생기는 표면의 규율

- 새 탭·API는 전부 `proxy.ts` 게이트 뒤. 공개 예외는 여전히 `/l/` `/hub` `/expired/`뿐.
- 공유 타깃 엔드포인트는 `/api/capture`를 그대로 쓴다 — 게이트 뒤이므로 쿠키 없는 공유는 401. 첫 1회 `?k=` 부트스트랩은 그대로.
- 성과 집계·허브 배지·홈 요약은 **DB만 읽는다**. 페이지뷰가 무신사 요청을 만들지 않는다.
- 정산 스크린샷도 이미지 미저장([06 §4.3]) 규칙 동일.
- 허브 배지는 스냅샷이 말하는 것만 말한다 — "최저가"는 우리가 기록한 범위 안의 최저가이며, 허브 각주에 그렇게 적는다.

### 4.0 V2-A에서 계획과 달라진 것 (2026-09-15)

구현하면서 실제로 눌러보고 바꾼 네 가지. 전부 "덜 만드는" 쪽이다.

| 계획 | 실제 | 이유 |
|---|---|---|
| 하단 탭 4개 | **3개**(홈·딜·설정)로 시작, 성과는 V2-B에서 추가 | 내용이 없는 탭을 미리 만들지 않는다 — "없는 것을 그리지 않는다"(§3.5-4)를 탭에도 적용 |
| `Deal.archivedAt` 컬럼 | **파생 판정**(APPROVED + 생성 30일 경과) | 컬럼을 채워줄 크론이 없으면 값이 영영 비어 있다. 지금 필요한 건 목록에서 빠지는 것뿐이라 계산으로 충분하고, 마이그레이션이 0건이 된다 |
| FAB은 모든 탭에 | 설정 탭에서는 **숨김** | 실기기 폭에서 떠 있는 FAB이 [작년 BF 가격 기록] 버튼을 실제로 가렸다. 설정은 캡처가 다음 동작이 아닌 유일한 탭이다 |
| `/watch` 폐기 | **리다이렉트로 유지** (`/deals?f=saved`) | 폰 홈 화면·북마크에 남아 있을 수 있다 |

`ScreenshotCapture`·`AppHeader`는 역할이 FAB·`PageHeader`로 옮겨가 삭제했고, 상태 카드
(`DealStageCard`)와 버튼 문구([06 §3.0])는 **한 글자도 바꾸지 않았다** — 놓이는 자리만 바뀌었다.

### 4.0.1 V2-B에서 정한 것 (2026-09-15)

- **막대는 한 색이다.** 계열이 하나(클릭 수)뿐이라 지면·딜마다 색을 주지 않는다. 색으로 크기를
  두 번 말하면(길이 + 명도) 정작 쓸 수 있는 채널을 낭비하고, 색맹 조건에서 먼저 깨진다.
  이름과 값이 **둘 다 글자로** 적혀 있어 막대는 차이만 거든다 — 값을 읽으려고 툴팁을 띄우거나
  길이를 잴 필요가 없다(= 별도 표 보기가 필요 없다).
- **변화량에 빨강을 쓰지 않는다.** 올라가면 초록, 내려가거나 같으면 회색이다. 지난주보다 클릭이
  적은 것은 경보가 아니고, 빨강을 여기 쓰면 진짜 경고(품절·고지 실패)와 색이 겹친다.
- **비교 기준은 화면에 한 번만.** "직전 7일 대비"를 타일마다 적으면 폰 3열에서 줄이 밀려
  타일 높이가 제각각이 된다(실기기 확인 후 수정).
- **카톡 페이스는 미터로.** 상한이 있는 값 하나는 막대그래프가 아니라 미터다([02 §7.5] 일 3~5건
  권고). 막지 않고 보여주기만 한다 — 전송은 사람이 하고 도구는 페이스를 안다.
- **허브 CTR의 분모(방문)가 없어 새 테이블이 하나 생겼다**(`HubVisit`). `ClickEvent`와 같은
  규율이다: IP·referer를 저장하지 않고 봇 분류만 남긴다. 기록 실패가 허브 렌더를 막지 않는다.
- 헤드리스 브라우저의 기본 UA는 앱이 **봇으로 분류해 집계에서 뺀다** — 검증 스크립트가 사람 UA를
  쓰도록 고쳤다(앱이 맞고 테스트가 틀린 경우였다).

### 4.0.2 V2-D에서 정한 것 (2026-09-15)

- **배지는 딜당 하나다.** 우선순위는 쿠폰 마감 > 최저가 > 가격 인하. 셋을 다 붙이면 아무것도
  강조하지 않는 것과 같다.
- **"최저가"는 표본 3건부터** 말한다(`MIN_LOWEST_SAMPLES`). 2건짜리 최저가는 그냥 "지난번보다
  싸다"이고, 그건 '가격 인하'가 이미 말한다. 수동 입력(작년 행사가)은 표본에서 뺀다 —
  `price-analysis`의 기준가 규율과 같다.
- **쿠폰 마감은 7일 안쪽만** 배지가 된다(`COUPON_URGENT_DAYS`). 한 달 남은 쿠폰은 급한 소식이
  아니면서 더 나은 배지를 밀어낸다.
- **각주로 범위를 밝힌다.** "‘최저가’는 제가 기록해 온 가격 범위 안에서의 최저가입니다" —
  최저가 배지가 실제로 하나라도 있을 때만 각주를 그린다. 우리가 가진 근거 이상을 말하지 않는다.
- **태그가 여러 개면 그 딜은 각 섹션에 함께 걸린다**(컬렉션과 같은 뜻). 태그 없는 딜은 마지막
  "오늘의 꿀매" 섹션에 모인다 — 태그를 하나도 안 쓰면 화면은 v1과 똑같다.
- **프로필 편집을 설정에 넣으면서 큐레이션 샵 주소도 함께 받게 했다.** 공개 허브에 링크로 실리는
  값이라 서버에서 **https + 무신사 도메인만** 통과시킨다(`profile.ts`) — `javascript:` 같은 스킴과
  엉뚱한 도메인이 공개 지면에 실리는 사고를 함께 막는다.
- 계획에 있던 "최신 / 많이 본 두 블록, 순서는 설정에서"는 **넣지 않았다.** 딜 허브는 최신순이
  기본값으로 맞고, 정렬 선택지를 설정에 하나 더 두는 값이 1인 사용에서 크지 않다. 필요해지면
  클릭 수는 이미 성과 탭에 있으니 그때 붙인다.

### 4.1 리스크

| 리스크 | 대응 |
|---|---|
| iOS에서 Web Share Target 불가 | 처음부터 iOS는 단축어 경로로 설계. FAB 경로는 양쪽 동일 |
| 시트 UI가 폰 브라우저에서 스크롤 충돌 | `<dialog>` + `overscroll-behavior: contain`. 실기기 E2E(현재 Playwright 하네스 재사용) |
| 성과 숫자를 보고 발행 빈도를 올림 → 카톡 게시 빈도 가드([02 §7.5]) 초과 | 성과 탭에 일일 게시 카운터를 같이 표시. 도구가 페이스를 보여준다 |
| 허브 배지 오판(스냅샷 오독) | 표본 ≥3에서만 "최저가", 배지는 1개만, 각주 명시. Vision 오독은 승인 전 사람이 본다(기존) |
| `Deal.tags` 자유 입력이 지저분해짐 | 입력 시 기존 태그 자동완성. 1인 사용이라 정규화 테이블은 만들지 않는다 |
| PWA 캐시가 구버전을 보여줌 | 서비스워커는 **넣지 않는다**(manifest만). 오프라인 지원은 목표가 아니다 |

2. 사진 포스트·이미지 재게시 — [03].
3. 서비스워커·오프라인 — 캐시 사고 대비 이득이 없다.

5. 팔로워 계정·알림·채팅.
6. 다크/라이트 테마 토글 — 시스템 설정 따름(이미 그렇다).
