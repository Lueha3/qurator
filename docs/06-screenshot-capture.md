# 06. 스크린샷 캡처 — 요청 0건으로 상품을 읽는다

> **한 줄 결론**: 무신사에 요청을 보내니까 막힌다(robots.txt·Cloudflare·둘 다 실측 확정, [05 §9]).
> **안 보내면 된다.** 현표가 자기 폰으로 자기 화면을 찍어 웹앱에 올리면, 앱이 읽는다.
>
> 이건 우회가 아니라 **더 나은 경로**다: 로그인 상태의 쿠폰 적용가까지 화면 그대로 읽히고(API로는 영영 못 얻는 값),
> 무신사 입장에서 현표는 그냥 앱 사용자이며, 모바일에서 완결된다.
>
> 결정 기록 (2026-09-09): 스크린샷을 **1차 입력 경로**로 확정. 링크 던지기는 보조(상품 식별용)로 격하.

---

## 0. 왜 이것뿐인가 — 검토한 대안

| 대안 | 판정 | 한 줄 이유 |
|---|---|---|
| UA를 Googlebot/ClaudeBot으로 위장 | ❌ 영구 금지 | Never List #7. 뚫는 순간 계정 리스크가 법적 리스크로 바뀐다 |
| robots.txt 무시 | ❌ 영구 금지 | 여기어때 판례의 안전선("보호조치 우회 안 함")을 스스로 넘는 것 |
| `goods-detail.musinsa.com` 등 API 서브도메인 | ❌ 하지 않음 | 호스트는 다르지만 의도는 같다. 규칙의 문자가 아니라 정신을 지킨다 |
| 메신저 링크 미리보기 | ❌ 불가 | 그들의 크롤러는 허용되지만 API가 미리보기 내용을 주지 않는다 |
| 크롬 확장 (사람이 보는 페이지 DOM 읽기) | △ 보조 | 요청 0건이라 정당하지만 PC 전용 — 현표의 동선은 모바일 앱이다 |
| 무신사 협의로 `HoneyFlowBot` 화이트리스트 | △ 장기 | 정공법이지만 몇 주~몇 달, 불확실. 성사돼도 데이터센터 IP는 별도 차단([05 §9.2]) |
| **스크린샷 → Vision** | ✅ **채택** | 요청 0건 · 모바일 완결 · 쿠폰가 포함 · 오늘 만들 수 있다 |
| **공유 텍스트 파싱** | ✅ 보조 채택 | 무신사 앱 공유에 상품명이 딸려오면 공짜로 채워진다 (확인 필요) |

## 1. 목표 — 병목은 귀찮음이다

- **입력은 2탭**: ① 무신사 앱에서 스크린샷 ② 웹앱에서 [스크린샷 올리기]로 선택. 타이핑 0.
- **출력은 3초 뒤 한 장의 판정 카드**: 바쁜 사람이 슥 보고 "올릴까 말까"를 정한다.
- **매출 직결**: 큐레이터의 수익 = 진짜 딜을 골라 올리는 것. 카드의 첫 줄이 그 판단을 대신한다.

하지 않는 것: 웹 대시보드를 열게 하지 않는다(폰에서 끝난다), 링크를 따로 붙이라고 하지 않는다(있으면 좋고 없어도 된다), 무신사에 요청을 보내지 않는다.

## 2. 사용자 흐름 (현표, 폰)

> 2026-09-14: 입력 채널이 텔레그램 봇 → **웹앱**으로 바뀌었다([02 §6]). 화면과 버튼의 의미는 그대로다.

```
무신사 앱에서 상품 발견
  → 스크린샷 (볼륨+전원)
  → 웹앱(홈 화면 아이콘) → [📷 스크린샷 올리기] → 방금 찍은 사진 선택
  → 3초 뒤 판정 카드 ─┬─ [✅ 이 상품 올릴게요] → 큐레이터 링크 붙여넣기 → 승인 → 카톡 문구
                       ├─ [📈 가격만 지켜보기] → 워치 등록 (리마인더 대상)
                       ├─ [✔️ 기록 완료]      → 카드만 닫음 (가격은 이미 저장됨)
                       └─ [✏️ 정보 고치기] · [❓ 버튼 설명]
```

스크린샷 1장이 하는 일 세 가지: **① 상품 인식 ② 가격 스냅샷 기록 ③ 판정** — 전부 자동.

링크는 언제 필요한가: 발행할 때만. 그것도 큐레이터센터에서 만든 링크를 붙여넣는 기존 단계에서 goodsNo가 확정되므로, **상품 URL을 따로 던질 일이 없어진다.**

## 3. 판정 카드 — 이것이 제품이다

```
🔥 진짜 딜 — 45일 최저가

쿠어 · 스탠다드 오버셔츠
89,000 → 53,400 (40%) · 쿠폰가 45,000

가격 흐름
  오늘        45,000  ← 쿠폰가
  8/28        55,000
  8/12        55,000
  작년 BF     39,900  (수동)

기준가 55,000 대비 실할인 18%
```
```
[      ✅ 이 상품 올릴게요      ]
[ 📈 가격만 지켜보기 ] [ ✔️ 기록 완료 ]
[  ✏️ 정보 고치기  ] [ ❓ 버튼 설명 ]
```

### 3.0 버튼 문구 규칙 (2026-09-10 재구성)

초기 문구(`[이거 올릴래] [스킵] [직접 입력] [BF 추적]`)는 **딜 레이더 시절의 유물**이었다 —
기계가 후보를 제안하고 사람이 골라내는 흐름에서는 "스킵"이 자연스럽다. 그러나 크롤링이 막혀
스크린샷이 1차 입력이 된 지금은 **사람이 이미 찍어서 올린 것**이므로 "버린다"는 프레임이 맞지 않는다.

재구성의 근거가 된 사실 두 가지 — 설명서(`BUTTON_GUIDE`)도 이 둘을 반드시 말한다:

1. **스크린샷을 받은 순간 가격은 이미 기록된다.** 버튼은 "그 다음에 무엇을 할지"를 고를 뿐이다.
   그래서 `스킵` → `✔️ 기록 완료`(삭제가 아니라 발행만 안 함).
2. **[올릴게요]는 즉시 발행이 아니다.** 링크 → 승인 단계가 남아 있다(approval-first 불변식, §7).

그 외: `BF 추적` → `📈 가격만 지켜보기`(내부 약어 제거), `직접 입력` → `✏️ 정보 고치기`
(이제 카드 안에서 폼이 바로 열린다 — 화면 이동이 없다).
주 동작은 한 줄을 독점하고, 나머지는 "올리지 않는다"는 점에서 같은 급이라 아래 줄에 묶는다.

> **2026-09-18 갱신 ([08 §4.0.7])**: 같은 의미를 더 짧게 — `✅ 이 상품 올릴게요` → `✅ 올릴게요`,
> `✔️ 기록 완료` → `📁 보관`, `🚀 승인 — 카톡 문구 받기` → `🚀 카톡 문구 받기`, `링크 붙여넣기 → 카드 만들기` →
> `🔗 링크 붙이기`, `🚫 품절로 표시` → `🚫 품절됐어요`. `❓ 버튼 설명` 버튼은 접이식 "버튼이 뭐예요?"로.
> 위 두 사실(기록은 이미 됐다 / 올릴게요는 즉시 발행이 아니다)은 그 설명이 그대로 말한다. 단계 표시명도
> 후보·링크 대기·승인 대기·승인 완료·기록 완료 → **올릴지 정하기·링크 붙이기·문구 확정하기·확정됨·안 올림**(코드 식별자는 그대로).
> 같은 날 검수 뒤: `🚀 카톡 문구 받기` → `✅ 이 문구로 확정하기`(누르면 팔로워 페이지에 올라간다는 사실을 이름이 말해야 한다),
> 보조 버튼은 이모지 없이(`안 올릴게요` · `가격만 지켜보기` · `정보 고치기` · `품절로 표시하기`). 이유는 [08 §4.0.7].

### 3.1 첫 줄 = 판정 (policy 키로 임계값 관리, [02 §13] 원칙)

| 판정 | 조건 | 뜻 |
|---|---|---|
| ⚠️ **위장 할인 의심** | 정가 대비 ≥30% 표기 **그런데** 기준가 대비 실할인 <10% | 정가를 올려놓고 할인처럼 보이게 한 것. **올리면 팔로워 신뢰를 잃는다** |
| 🔥 **진짜 딜** | 기준가 대비 실할인 ≥15% | 평소보다 실제로 싸다 |
| 📉 **최저가 경신** | 기록된 모든 스냅샷보다 낮음 (배지, 위 판정에 덧붙음) | "지금까지 본 것 중 제일 쌈" |
| 😐 **평소 가격** | 실할인 ±5% 이내 | 할인 표기가 있어도 평소와 같다 |
| 🆕 **첫 기록** | 기준가 없음 (표본 <3) | "정가 대비 N% · 기준가 수집 시작" — 판정하지 않는다 |

우선순위: 위장 의심 > 진짜 딜 > 평소 가격 > 첫 기록. 계산은 전부 기존 `price-analysis.ts`(§4.4 기준가 중앙값·실할인율)를 재사용한다 — **새 수학은 없다.**

### 3.2 가격 흐름 (최근 3개 + 작년 행사)

스냅샷에서 최신 3건 + eventTag가 붙은 행사 대표가. 수동 입력은 `(수동)` 배지. 스냅샷이 1건뿐이면 "첫 기록"만 표시하고 흐름은 생략.

### 3.3 읽지 못했을 때

- 상품 페이지가 아님(장바구니·옵션 시트·홈): "상품 페이지 **상단**(브랜드·상품명·가격이 보이는 화면)을 찍어주세요"
- 가격은 읽었는데 상품명이 흐림: 카드는 띄우되 `⚠️ 상품명 확인 필요` + [✏️ 정보 고치기]
- Vision 실패(API 장애·타임아웃): 기존 ai-hook 패턴대로 **null → 빈 카드 + 직접 입력**. 파이프라인은 멈추지 않는다.

## 4. 인식 설계

### 4.1 Vision 추출 (Claude, 구조화 출력)

- 모델: `claude-opus-5` (`output_config.effort: "low"` — 추출은 깊은 사고가 필요 없다). 서버측 `fallbacks: "default"` 포함.
- 입력: 스크린샷 1장(base64) + 지시 "무신사 상품 페이지 스크린샷. **보이는 것만** 추출, 추측 금지, 원 단위 정수".
- 출력 스키마 (`output_config.format`):

```
isProductPage      boolean      상품 페이지 상단인가
brand              string|null
productName        string|null
styleCode          string|null  품번이 보이면
listPrice          int|null     정가 (취소선·"정가")
salePrice          int|null     판매가·할인가 (가장 크게 표시된 현재가)
couponPrice        int|null     쿠폰 적용가·최대혜택가 (표시된 경우만)
discountRateShown  int|null     화면에 찍힌 %
soldOut            boolean|null
confidence         high|medium|low
notes              string|null  애매한 점 ("가격이 두 개 보임" 등)
```

- **가격이 하나도 안 읽히면 스냅샷을 남기지 않는다** ([05 §4.3] 원칙 동일 — 오염된 기준가가 최악).
- `couponPrice`는 **로그인 상태 화면값**이다. 등급할인이 섞여 있을 수 있음 — 스냅샷에 그대로 저장하되, 카드에는 "쿠폰가"로 표기하고 어떤 쿠폰인지는 단정하지 않는다.

### 4.1.1 같은 상품을 다시 찍었을 때 — 카드를 새로 만들지 않는다 (2026-09-16)

**운영에서 발견한 것**: 후보 카드가 13장까지 불어났고 그중 상당수가 같은 상품이었다.
원인은 구조적이다 — 홈 리마인더가 매일 "오늘 가격을 기록할 상품 N개, 다시 찍어 올려주세요"라고
조르는데([05 §3.4], 크롤리스 모드에서 기준가가 쌓이는 유일한 경로다), 캡처마다 딜을 만들면
**워치 3개 × 매일 = 하루 3장씩 영원히** 쌓인다. 딜 탭이 "지금 할 일"을 보여주는 화면이기를
그만두는 것이다.

그래서 캡처는 이제 이렇게 갈린다:

| 그 상품의 상태 | 동작 |
|---|---|
| 아직 손대지 않은 딜이 있다 (후보·링크 대기·승인 대기) | **그 딜을 갱신**하고 같은 카드를 연다. 가격 기록은 따로 쌓인다 |
| 승인 완료·기록 완료만 있다 | 새 후보 딜을 만든다 — 끝난 판단이고, 다시 찍었다는 건 새로 판단할 일이 생겼다는 뜻이다 |

갱신 규칙 두 가지:
- **이번에 못 읽은 값으로 이미 있던 값을 지우지 않는다** (`result.salePrice ?? open.salePrice`).
  두 장 중 한 장만 잘 찍힌 경우에 이전 판독을 날리면 안 된다.
- **승인 대기 딜이면 카드를 다시 렌더한다** — "본 것 = 나가는 것"([02 §6])이므로, 가격이 바뀐 뒤에도
  옛 가격이 담긴 카드가 고지문과 함께 나가면 안 된다.

사람에게도 다르게 말한다: 새로 만들면 "카드를 만들었습니다", 재사용하면
**"이미 있던 카드에 가격을 기록했습니다"**. 카드가 원래 있었는데 새로 만들었다고 하면 거짓말이다.

#### 이미 쌓인 중복 정리 — 설정 탭의 [중복 카드 정리]

고치기 전에 쌓인 카드는 한 번 걷어내야 한다. **설정 탭 → 중복 카드 정리**에서
[중복 카드 확인]을 누르면 무엇을 닫을지 먼저 보여주고, 그 화면에서 누른 뒤에만 바뀐다.
앱이 이미 들고 있는 DB 연결을 쓰므로 PC도, `.env`도 필요 없다.

같은 일을 PC에서 하고 싶으면 CLI도 있다(규칙은 `src/lib/dedupe.ts` 한 벌을 공유한다):

```bash
npm run db:dedupe             # 무엇을 닫을지 보여주기만 한다
npm run db:dedupe -- --apply  # 실제로 닫는다
```

- **지우지 않는다.** '기록 완료'(SKIPPED)로 바꿀 뿐이라 가격 기록도 딜 행도 그대로 남는다.
- **사람 손이 닿은 카드는 자동으로 닫지 않는다.** 큐레이터 링크나 완성된 카드가 붙어 있으면
  목록에만 띄우고 넘어간다 — 링크를 만드는 데 든 시간이 이 스크립트보다 비싸다.
- **남기는 것은 가장 앞서 나간 카드**(승인 대기 > 링크 대기 > 후보, 같으면 최신).
  진행 중이던 판단을 되돌리지 않기 위해서다.
- 감사 로그에 `deal.deduped`로 남고, 다시 돌려도 같은 결과다(멱등).

### 4.2 상품 매칭 — 어느 Product에 붙일 것인가

> **구현 후 발견(2026-09-09, 적대적 검증)**: 아래 4단계 매칭과 별개로, S0 최초 구현에는
> "나중에 큐레이터 링크가 오면 그 Product에 goodsNo를 채운다"가 실제로 구현돼 있지 않았다.
> `handleCuratorLinkPaste`가 백필하도록 수정하고(§4.2 마지막 단락), goodsNo 충돌 시엔
> 경고만 남기고 sentinel을 유지한다. 추가로 `health-check.ts`·`watch.ts`에 방어선을 넣었다 —
> canonicalUrl이 유효한 무신사 URL이 아니면 게이트웨이를 부르지 않고 그 항목만 건너뛴다
> (백필이 어떤 이유로든 안 됐을 때, `BLOCKED_POLICY`가 STOP_CYCLE_OUTCOMES라서 사이클
> 전체가 멈추는 사고를 막는 이중 방어).

순서대로, 처음 맞는 것:

1. **같은 대화, 10분 이내에 goodsNo가 있는 딜**이 있으면 그 상품 (링크 먼저 던진 경우)
2. `styleCode` 정확 일치 (creator 범위)
3. `(brand, productName)` 정규화 일치 — 소문자·공백·특수문자 제거. 무신사 상품명은 길고 구체적이라 한 큐레이터의 수십 개 상품 안에서 충돌은 드물다
4. 없으면 **신규 Product** (`musinsaGoodsNo = null`, `source = SCREENSHOT`)

나중에 큐레이터 링크가 오면(`parseCuratorLink`가 goodsNo를 준다) 그 Product에 goodsNo를 채운다. 이미 같은 goodsNo의 Product가 있으면 경고 로그 + 링크는 기존 상품에 붙인다(자동 병합은 v2).

### 4.3 이미지는 저장하지 않는다

스크린샷에는 알림바·닉네임·다른 앱 알림이 찍힌다. 규칙:
- 업로드를 받아 **메모리에서** Claude로 보내고 **즉시 버린다.** 디스크·DB·로그 어디에도 쓰지 않는다.
- 저장하는 것은 추출된 필드뿐 (기존 FetchLog "본문 미저장" 원칙의 확장).
- Anthropic API는 기본 정책상 API 입력을 학습에 쓰지 않는다. 그래도 위 규칙이 먼저다.

### 4.4 웹 업로드 수신 (2026-09-14: 텔레그램 수신에서 전환)

`<input type="file" accept="image/*" multiple>` → 브라우저에서 긴 변 1600px로 리사이즈(JPEG q0.85) →
`POST /api/capture` (multipart) → base64 → Claude. 리사이즈는 요청 본문을 서버리스 한도 안에 두기
위한 것이고, 작은 글씨(품번)를 읽어야 하므로 필요 이상으로 줄이지 않는다.

- **서버 액션이 아니라 라우트 핸들러다**: 서버 액션 본문은 기본 1MB 상한이라 폰 스크린샷 몇 장이면
  넘는다. 라우트는 `maxDuration = 60`(Vision 20초 + DB 왕복)과 자체 용량 상한(12MB)을 갖는다.
- 이 라우트는 `proxy.ts`의 `APP_ACCESS_TOKEN` 게이트 뒤에 있다 — 공개 경로가 아니다.

### 4.4.1 여러 장을 한 캡처로 — 한 화면에 상품과 가격이 다 안 담길 때

무신사 상품 페이지는 상품명·이미지가 위쪽, 가격·쿠폰가가 스크롤한 아래쪽에 있어 폰 화면 하나로
안 담기는 경우가 흔하다(특히 iPhone — 스크롤 캡처가 앱엔 안 먹힌다, Android 기종은 스크롤 캡처로
애초에 회피 가능). 해결책: **2장으로 나눠 찍어 파일 선택에서 함께 고르면** 한 캡처로 합쳐 읽는다.

- 여러 파일이 **한 요청**으로 오므로 텔레그램 시절의 버퍼링(`media_group_id` 디바운스,
  `AlbumCapture` 테이블, 리더 선출)이 통째로 사라졌다 — 앨범을 사진마다 별개 update로 쪼개 보내던
  텔레그램의 제약이 원인이었고, 그 제약이 없어졌기 때문이다(2026-09-14, 스키마에서도 제거).
- 모인 이미지들은 `extractFromScreenshot`에 **한 번에** 전달된다 — Claude에게 "같은 페이지를
  나눠 찍은 조각들"이라고 명시하고, 종합해서 하나의 JSON으로 답하게 한다(`vision-extract.ts`).
- 상한은 `MAX_CAPTURE_IMAGES`(4장) — 그 이상은 실수로 여러 상품을 같이 고른 경우로 보고
  이 캡처엔 쓰지 않는다(서버가 400으로 돌려준다).

### 4.5 아이폰 단축어 — 앱을 열지 않고 올리기 (2026-09-15)

웹앱을 여는 것 자체가 한 탭이다. 사진첩에서 스크린샷을 고르는 것도 한 탭이다.
**공유 시트에서 바로 보내면 둘 다 사라진다** — 무신사 앱에서 스크린샷을 찍고 공유만 누르면 끝이다.

Android의 `manifest.share_target`은 PWA 표준이지만 **iOS는 지원하지 않는다**(2026-09 기준).
사용 기기가 아이폰이므로 본선은 **단축어(Shortcuts)**다.

#### 누가 설치하는가: **관리자가 현표 폰에서 직접 만든다** (2026-09-18 확정)

레시피 3번의 헤더 값은 `APP_ACCESS_TOKEN` — **마스터 토큰**이다. [03 §7.2]가 1회용 등록 초대를
만든 이유가 바로 "등록시키려고 마스터 토큰을 넘기게 된다"였는데, 단축어 설치를 현표에게 맡기면
그 토큰을 카톡으로 보내게 되어 같은 구멍이 다시 열린다.

그래서 **설정 화면에서 이 레시피를 뺐다.** 화면에는 "관리자에게 한 번 부탁하면 단축어를 만들어 줘요"
한 줄만 있다(`src/app/(app)/settings/page.tsx`). 설치는 관리자가 현표 폰을 한 번 잡고 직접 한다 —
토큰은 관리자 손에서 단축어 안으로만 들어가고, 채팅·화면·문서 어디에도 남지 않는다.

단축어 전용 토큰을 따로 발급하는 방안(권한을 `/api/capture`로만 좁힌 두 번째 토큰)은 **하지 않는다**:
게이트가 토큰 하나를 전제로 짜여 있어(`proxy.ts`) 두 번째 토큰은 그 게이트를 고치는 일이고,
1인 사용에서 그만큼의 표면을 늘릴 이유가 없다. 폰을 잃어버렸을 때의 대응은 그때도 같다 —
`APP_ACCESS_TOKEN`을 바꾸고 단축어를 다시 만든다.

#### 서버 쪽 준비: `x-app-token` 헤더

단축어는 쿠키를 들고 다니지 못한다. 그래서 `src/proxy.ts`가 토큰을 헤더로도 받는다:

```
x-app-token: <APP_ACCESS_TOKEN>
```

`?k=`를 쓰지 않는 이유는 그 경로가 **쿠키를 심고 리다이렉트**하기 때문이다 — 업로드 POST를
리다이렉트에 태우면 본문 처리가 클라이언트 구현에 달린다. 헤더는 한 번에 끝나고, 토큰이
주소·리퍼러·서버 로그의 URL에 남지 않으며, 크로스사이트 폼은 커스텀 헤더를 붙일 수 없어
CSRF 표면도 쿠키보다 좁다. 헤더로 통과한 요청은 **쿠키를 심지 않는다**(그 요청 하나만 통과).

#### 단축어 레시피

1. 단축어 앱 → **새 단축어** → 이름 `꿀매 올리기`
2. **이미지 크기 조절** 추가 — 입력: `단축어 입력`, 가장 긴 변 **1600px**
   > 이 단계를 빼지 않는다. 서버리스 요청 본문 상한(플랜에 따라 4.5MB)에 폰 스크린샷
   > 두 장이면 닿는다. 웹앱도 같은 값으로 줄여서 보낸다(§4.4).
3. **URL 내용 가져오기** 추가
   - URL: `https://<배포 주소>/api/capture`
   - 방식: `POST`
   - 헤더: `x-app-token` = Vercel 환경변수의 `APP_ACCESS_TOKEN` 값
   - 본문: `양식(Form)` → 필드 이름 `images`, 종류 `파일`, 값 `크기 조절된 이미지`
4. (선택) **사전 값 가져오기** `kind` → **알림 표시**로 결과 확인
5. 단축어 설정(ⓘ) → **공유 시트에 표시** 켜기 → 입력 종류에서 `이미지`만 남기기

이후 흐름: 무신사 앱 → 스크린샷 → 공유 → `꿀매 올리기` → 끝.
카드는 다음에 웹앱을 열 때 딜 탭 맨 위에 있다(`kind: "created"`).

여러 장을 한 상품으로 합쳐 읽히려면(§4.4.1) 사진 앱에서 **두 장을 함께 선택해 공유**한다 —
`images` 필드가 반복되어 한 요청으로 올라간다.

## 5. 링크 경로 보강 (보조)

### 5.1 onelink 리다이렉트 도착 URL에서 goodsNo 추출 — 무신사 요청 0건

지금: `onelink.me → 301 → musinsa.com/products/123` 에서 게이트웨이가 musinsa.com을 robots로 거부하며 **도착 URL을 버린다** → goodsNo = null → 같은 상품을 두 번 던지면 두 개가 생긴다.
고침: 거부 결과에 `landedUrl`을 실어 보낸다(3줄). 핸들러가 거기서 goodsNo·canonicalUrl을 뽑는다. **onelink.me까지만 요청하고 musinsa.com은 건드리지 않는다** — 지금과 요청 수가 같다.

### 5.2 공유 텍스트 파싱

무신사 앱 "공유하기"가 링크만 보내는지, 상품명이 딸려오는지 **현표가 한 번 확인**. 딸려오면 정규식으로 브랜드·상품명을 채운다. 비용 0.

## 6. BF 추적과의 연결

[05 §3.4] 크롤리스 모드의 리마인더(`npm run remind`)가 이미 "오늘 기록할 상품 N개"를 보낸다. 거기에:
- 상품별 **앱 열기 링크**(canonicalUrl — 탭하면 무신사 앱이 열린다)
- 안내 문구를 "다시 던져주세요" → "**열어서 찍어 보내주세요**"로

현표: 탭 → 찍기 → 공유. 봇: 4.2 매칭으로 그 상품에 스냅샷 기록(행사 창이면 eventTag 자동). **자동 요청 0건으로 BF 기준가와 행사가가 쌓인다.**

## 11. [05]와의 관계

[05 §3.4] 크롤리스 모드의 "USER_URL(링크 재던지기)로만 축적"을 **"스크린샷으로 축적"**으로 대체한다.
