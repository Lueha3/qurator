# 06. 스크린샷 캡처 — 요청 0건으로 상품을 읽는다

> **한 줄 결론**: 무신사에 요청을 보내니까 막힌다(robots.txt·Cloudflare·둘 다 실측 확정, [05 §9]).
> **안 보내면 된다.** 현표가 자기 폰으로 자기 화면을 찍어 봇에 올리면, 봇이 읽는다.
>
> 이건 우회가 아니라 **더 나은 경로**다: 로그인 상태의 쿠폰 적용가까지 화면 그대로 읽히고(API로는 영영 못 얻는 값),
> 무신사 입장에서 현표는 그냥 앱 사용자이며, 모바일에서 완결된다.
>
> 결정 기록 (2026-09-09): 스크린샷을 **1차 입력 경로**로 확정. 링크 던지기는 보조(상품 식별용)로 격하.

---

## 0. 왜 이것뿐인가 — 검토한 대안

| 대안 | 판정 | 한 줄 이유 |
|---|---|---|
| UA를 Googlebot/ClaudeBot으로 위장 | ❌ 영구 금지 | Never List #7. 뚫는 순간 계정 리스크가 법적 리스크로 바뀐다 |
| robots.txt 무시 | ❌ 영구 금지 | 여기어때 판례의 안전선("보호조치 우회 안 함")을 스스로 넘는 것 |
| `goods-detail.musinsa.com` 등 API 서브도메인 | ❌ 하지 않음 | 호스트는 다르지만 의도는 같다. 규칙의 문자가 아니라 정신을 지킨다 |
| 텔레그램·카카오 링크 미리보기 | ❌ 불가 | 그들의 크롤러는 허용되지만 봇 API가 미리보기 내용을 주지 않는다 |
| 크롬 확장 (사람이 보는 페이지 DOM 읽기) | △ 보조 | 요청 0건이라 정당하지만 PC 전용 — 현표의 동선은 모바일 앱이다 |
| 무신사 협의로 `HoneyFlowBot` 화이트리스트 | △ 장기 | 정공법이지만 몇 주~몇 달, 불확실. 성사돼도 데이터센터 IP는 별도 차단([05 §9.2]) |
| **스크린샷 → Vision** | ✅ **채택** | 요청 0건 · 모바일 완결 · 쿠폰가 포함 · 오늘 만들 수 있다 |
| **공유 텍스트 파싱** | ✅ 보조 채택 | 무신사 앱 공유에 상품명이 딸려오면 공짜로 채워진다 (확인 필요) |

## 1. 목표 — 병목은 귀찮음이다

- **입력은 2탭**: ① 무신사 앱에서 스크린샷 ② 텔레그램 봇에 공유. 타이핑 0.
- **출력은 3초 뒤 한 장의 판정 카드**: 바쁜 사람이 슥 보고 "올릴까 말까"를 정한다.
- **매출 직결**: 큐레이터의 수익 = 진짜 딜을 골라 올리는 것. 카드의 첫 줄이 그 판단을 대신한다.

하지 않는 것: 웹 대시보드를 열게 하지 않는다(폰에서 끝난다), 링크를 따로 붙이라고 하지 않는다(있으면 좋고 없어도 된다), 무신사에 요청을 보내지 않는다.

## 2. 사용자 흐름 (현표, 폰)

```
무신사 앱에서 상품 발견
  → 스크린샷 (볼륨+전원)
  → 썸네일 탭 → 공유 → 텔레그램 → 봇
  → 3초 뒤 판정 카드 ─┬─ [✅ 이거 올릴래] → (기존 흐름) 큐레이터 링크 붙여넣기 → 승인 → 카톡 문구
                       ├─ [📈 BF 추적]   → 워치 등록 (리마인더 대상)
                       └─ [⏭ 스킵]
```

스크린샷 1장이 하는 일 세 가지: **① 상품 인식 ② 가격 스냅샷 기록 ③ 판정** — 전부 자동.

링크는 언제 필요한가: 발행할 때만. 그것도 큐레이터센터에서 만든 링크를 붙여넣는 기존 단계에서 goodsNo가 확정되므로, **상품 URL을 따로 던질 일이 없어진다.**

## 3. 판정 카드 — 이것이 제품이다

```
🔥 진짜 딜 — 45일 최저가

쿠어 · 스탠다드 오버셔츠
89,000 → 53,400 (40%) · 쿠폰가 45,000

가격 흐름
  오늘        45,000  ← 쿠폰가
  8/28        55,000
  8/12        55,000
  작년 BF     39,900  (수동)

기준가 55,000 대비 실할인 18%
```
`[✅ 이거 올릴래]  [📈 BF 추적]  [⏭ 스킵]`

### 3.1 첫 줄 = 판정 (policy 키로 임계값 관리, [02 §13] 원칙)

| 판정 | 조건 | 뜻 |
|---|---|---|
| ⚠️ **위장 할인 의심** | 정가 대비 ≥30% 표기 **그런데** 기준가 대비 실할인 <10% | 정가를 올려놓고 할인처럼 보이게 한 것. **올리면 팔로워 신뢰를 잃는다** |
| 🔥 **진짜 딜** | 기준가 대비 실할인 ≥15% | 평소보다 실제로 싸다 |
| 📉 **최저가 경신** | 기록된 모든 스냅샷보다 낮음 (배지, 위 판정에 덧붙음) | "지금까지 본 것 중 제일 쌈" |
| 😐 **평소 가격** | 실할인 ±5% 이내 | 할인 표기가 있어도 평소와 같다 |
| 🆕 **첫 기록** | 기준가 없음 (표본 <3) | "정가 대비 N% · 기준가 수집 시작" — 판정하지 않는다 |

우선순위: 위장 의심 > 진짜 딜 > 평소 가격 > 첫 기록. 계산은 전부 기존 `price-analysis.ts`(§4.4 기준가 중앙값·실할인율)를 재사용한다 — **새 수학은 없다.**

### 3.2 가격 흐름 (최근 3개 + 작년 행사)

스냅샷에서 최신 3건 + eventTag가 붙은 행사 대표가. 수동 입력은 `(수동)` 배지. 스냅샷이 1건뿐이면 "첫 기록"만 표시하고 흐름은 생략.

### 3.3 읽지 못했을 때

- 상품 페이지가 아님(장바구니·옵션 시트·홈): "상품 페이지 **상단**(브랜드·상품명·가격이 보이는 화면)을 찍어주세요"
- 가격은 읽었는데 상품명이 흐림: 카드는 띄우되 `⚠️ 상품명 확인 필요` + [✏️ 직접 입력]
- Vision 실패(API 장애·타임아웃): 기존 ai-hook 패턴대로 **null → 빈 카드 + 직접 입력**. 파이프라인은 멈추지 않는다.

## 4. 인식 설계

### 4.1 Vision 추출 (Claude, 구조화 출력)

- 모델: `claude-opus-5` (`output_config.effort: "low"` — 추출은 깊은 사고가 필요 없다). 서버측 `fallbacks: "default"` 포함.
- 입력: 스크린샷 1장(base64) + 지시 "무신사 상품 페이지 스크린샷. **보이는 것만** 추출, 추측 금지, 원 단위 정수".
- 출력 스키마 (`output_config.format`):

```
isProductPage      boolean      상품 페이지 상단인가
brand              string|null
productName        string|null
styleCode          string|null  품번이 보이면
listPrice          int|null     정가 (취소선·"정가")
salePrice          int|null     판매가·할인가 (가장 크게 표시된 현재가)
couponPrice        int|null     쿠폰 적용가·최대혜택가 (표시된 경우만)
discountRateShown  int|null     화면에 찍힌 %
soldOut            boolean|null
confidence         high|medium|low
notes              string|null  애매한 점 ("가격이 두 개 보임" 등)
```

- **가격이 하나도 안 읽히면 스냅샷을 남기지 않는다** ([05 §4.3] 원칙 동일 — 오염된 기준가가 최악).
- `couponPrice`는 **로그인 상태 화면값**이다. 등급할인이 섞여 있을 수 있음 — 스냅샷에 그대로 저장하되, 카드에는 "쿠폰가"로 표기하고 어떤 쿠폰인지는 단정하지 않는다.

### 4.2 상품 매칭 — 어느 Product에 붙일 것인가

> **구현 후 발견(2026-09-09, 적대적 검증)**: 아래 4단계 매칭과 별개로, S0 최초 구현에는
> "나중에 큐레이터 링크가 오면 그 Product에 goodsNo를 채운다"가 실제로 구현돼 있지 않았다.
> `handleCuratorLinkPaste`가 백필하도록 수정하고(§4.2 마지막 단락), goodsNo 충돌 시엔
> 경고만 남기고 sentinel을 유지한다. 추가로 `health-check.ts`·`watch.ts`에 방어선을 넣었다 —
> canonicalUrl이 유효한 무신사 URL이 아니면 게이트웨이를 부르지 않고 그 항목만 건너뛴다
> (백필이 어떤 이유로든 안 됐을 때, `BLOCKED_POLICY`가 STOP_CYCLE_OUTCOMES라서 사이클
> 전체가 멈추는 사고를 막는 이중 방어).

순서대로, 처음 맞는 것:

1. **같은 대화, 10분 이내에 goodsNo가 있는 딜**이 있으면 그 상품 (링크 먼저 던진 경우)
2. `styleCode` 정확 일치 (creator 범위)
3. `(brand, productName)` 정규화 일치 — 소문자·공백·특수문자 제거. 무신사 상품명은 길고 구체적이라 한 큐레이터의 수십 개 상품 안에서 충돌은 드물다
4. 없으면 **신규 Product** (`musinsaGoodsNo = null`, `source = SCREENSHOT`)

나중에 큐레이터 링크가 오면(`parseCuratorLink`가 goodsNo를 준다) 그 Product에 goodsNo를 채운다. 이미 같은 goodsNo의 Product가 있으면 경고 로그 + 링크는 기존 상품에 붙인다(자동 병합은 v2).

### 4.3 이미지는 저장하지 않는다

스크린샷에는 알림바·닉네임·다른 앱 알림이 찍힌다. 규칙:
- 텔레그램에서 받아 **메모리에서** Claude로 보내고 **즉시 버린다.** 디스크·DB·로그 어디에도 쓰지 않는다.
- 저장하는 것은 추출된 필드뿐 (기존 FetchLog "본문 미저장" 원칙의 확장).
- Anthropic API는 기본 정책상 API 입력을 학습에 쓰지 않는다. 그래도 위 규칙이 먼저다.

### 4.4 텔레그램 수신

`message.photo[]`(압축 사진) → 가장 큰 사이즈 → `getFile` → `api.telegram.org/file/bot<token>/<path>` 다운로드 → base64.
텔레그램 압축(긴 변 ~1280px)은 무신사 앱의 큰 가격 글꼴엔 충분하다. 오독이 잦으면 "파일로 보내기" 안내를 추가한다 — 먼저 압축본으로 실측.

## 5. 링크 경로 보강 (보조)

### 5.1 onelink 리다이렉트 도착 URL에서 goodsNo 추출 — 무신사 요청 0건

지금: `onelink.me → 301 → musinsa.com/products/123` 에서 게이트웨이가 musinsa.com을 robots로 거부하며 **도착 URL을 버린다** → goodsNo = null → 같은 상품을 두 번 던지면 두 개가 생긴다.
고침: 거부 결과에 `landedUrl`을 실어 보낸다(3줄). 핸들러가 거기서 goodsNo·canonicalUrl을 뽑는다. **onelink.me까지만 요청하고 musinsa.com은 건드리지 않는다** — 지금과 요청 수가 같다.

### 5.2 공유 텍스트 파싱

무신사 앱 "공유하기"가 링크만 보내는지, 상품명이 딸려오는지 **현표가 한 번 확인**. 딸려오면 정규식으로 브랜드·상품명을 채운다. 비용 0.

## 6. BF 추적과의 연결

[05 §3.4] 크롤리스 모드의 리마인더(`npm run remind`)가 이미 "오늘 기록할 상품 N개"를 보낸다. 거기에:
- 상품별 **앱 열기 링크**(canonicalUrl — 탭하면 무신사 앱이 열린다)
- 안내 문구를 "다시 던져주세요" → "**열어서 찍어 보내주세요**"로

현표: 탭 → 찍기 → 공유. 봇: 4.2 매칭으로 그 상품에 스냅샷 기록(행사 창이면 eventTag 자동). **자동 요청 0건으로 BF 기준가와 행사가가 쌓인다.**

## 7. 안전 — 무엇이 바뀌고 무엇이 안 바뀌나

| 항목 | 상태 |
|---|---|
| 무신사로 나가는 요청 | 스크린샷 경로 **0건**. 링크 경로는 지금처럼 onelink.me까지만 |
| 현표 계정 | **변화 없음.** 자기 폰으로 자기 화면을 찍는 것 — 무신사에겐 앱 사용자일 뿐 |
| approval-first | 유지. Vision 값은 카드에 **표시**될 뿐, 사람이 [이거 올릴래]를 누르기 전엔 아무것도 나가지 않는다 |
| 고지 불변식·링크 불변식 | 무관 — 발행 단계는 손대지 않는다 |
| 이미지 | 저장 안 함 (§4.3) |
| 새 자격증명 | 없음. `ANTHROPIC_API_KEY`는 이미 있다 |

Fetch Gateway·robots·서킷·킬스위치는 그대로 두되, 스크린샷 경로는 애초에 게이트웨이를 **지나가지 않는다** — 외부 요청이 없으니까.

## 8. 개발 계획

| 단계 | 내용 | 완료 기준 | 규모 |
|---|---|---|---|
| **S0** | 사진 수신 → Vision 추출 → 후보 카드 + 스냅샷 기록. `SCREENSHOT` 출처 추가(CaptureSource·SnapshotSource) | ✅ **완료 (2026-09-09)** — `vision-extract.ts`·`product-match.ts`·핸들러 연결 + 4관점 적대적 검증(3 pass·1 fail→수정 완료) | 2일 |
| **S1** | **판정 카드**: §3.1 규칙(policy 키) + 가격 흐름 렌더. `price-analysis.ts` 재사용 | 같은 상품 3번째 스크린샷부터 실할인 판정이 첫 줄에 뜬다 | 1일 |
| **S2** | 상품 매칭(§4.2) · onelink `landedUrl` → goodsNo(§5.1) · 공유 텍스트(§5.2) | 링크→스크린샷, 스크린샷→링크 어느 순서로 와도 한 상품으로 합쳐진다 | 1일 |
| **S3** | 리마인더에 앱 열기 링크 + 문구(§6) · 워크스페이스 스트립에 SCREENSHOT 출처 표기 | BF 리마인더 → 찍기 → 스냅샷이 행사 태그를 달고 쌓인다 | 반나절 |

**S0만 끝나도 "찍어서 올린다"가 성립한다.** 나머지는 그 위에 얹는다. 총 5일 안팎.

### 8.1 비용

Opus 5 기준 스크린샷 1장 ≈ 입력 1,500토큰 + 출력 200토큰 ≈ **$0.013**. 월 200장 = $2.6 — [04 비용표] AI 상한($15/월) 안.
Haiku 4.5로 내리면 $0.002/장이지만, **가격 오독 1건이 팔로워 2,754명에게 나가는 비용이 훨씬 크다.** 정확도 우선, 측정 후 조정.

## 9. 리스크

| 리스크 | 대응 |
|---|---|
| Vision이 숫자를 잘못 읽음 (53,400 → 58,400) | `confidence`+`notes`를 카드에 반영, 사람이 승인 전 본다, [직접 입력] 폴백. 초기 2주 오독률 기록 |
| 상품 페이지가 아닌 화면을 찍음 | `isProductPage=false` → 안내 문구 (§3.3) |
| 같은 상품이 두 개로 생김 (매칭 실패) | styleCode·이름 매칭 + 큐레이터 링크 도착 시 goodsNo로 확정. v2에서 병합 명령 |
| 텔레그램 압축으로 작은 글씨 오독 | 큰 가격 글꼴은 안전. 품번 등 작은 글씨는 null 허용, "파일로 보내기" 안내 준비 |
| Claude API 장애 | null 폴백 → 빈 카드 + 직접 입력 (기존 패턴). 봇은 멈추지 않는다 |
| 스크린샷 개인정보 | 저장 안 함 (§4.3) |

## 10. 결정 필요 — 셋뿐
